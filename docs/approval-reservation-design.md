# 승인·예약 상태 및 트랜잭션 설계 v0.1

출고 이후의 전이·전체 완료 판정·진행 사유는 [보충 이행 상태 명세](fulfillment-state-design.md)를 함께 따른다.

관련 문서: [요구사항](requirements.md) · [모듈 설계](module-design.md) · [기술 스택](technology-stack.md)

## 1. 범위와 설계 가정

FR-02~05, FR-12~14 및 BR-01~03을 대상으로, 제출된 보충 요청의 승인·재고 예약과 출고 지시 생성 전 취소를 설계한다. SC-01·02를 직접 다루며 SC-03~06에 필요한 수량 경계를 정의한다.

이번 설계에서 추가로 정한 가정:

- 제출 후 요청 항목·수량·부분 이행 정책은 수정하지 않는다. 변경이 필요하면 출고 전 취소 후 새 요청을 만든다.
- 한 요청 안에 같은 SKU는 한 항목만 존재한다.
- 승인 한 번은 하나의 승인 회차다. 부분 이행 허용 요청의 미배정 잔량은 이후 별도 회차에서 추가 승인할 수 있다.
- 모든 항목이 0인 승인은 거절한다. 부분 이행 허용 시 일부 항목의 승인 수량은 0일 수 있다.
- 부분 이행 허용은 서버의 임의 자동 배정을 의미하지 않는다. 담당자가 지정한 수량을 원자적으로 예약한다.
- 초기 예약은 거점·SKU 단위다. 창고 세부 위치 배정과 대체 위치 확인은 WMS 책임이며 시뮬레이터 결과에 위치 ID를 포함한다.
- 위 정책은 프로젝트 설계 결정이며 실제 기업 운영 정책으로 주장하지 않는다.

## 2. 상태 모델

### 2.1 요청의 수명주기

| 현재 | 명령·조건 | 이후 | 재고 영향 |
|---|---|---|---|
| DRAFT | 제출, 유효한 SKU·양수 수량 | SUBMITTED | 없음 |
| SUBMITTED | 승인, 지정 수량 전부 예약 성공 | FULFILLING | 예약 증가 |
| SUBMITTED | 반려, 사유 필수 | REJECTED | 없음 |
| SUBMITTED | 소속 매장의 취소 | CANCELLED | 없음 |
| FULFILLING | 부분 이행 허용 잔량 추가 승인, 또는 부족 지시 취소 후 부분 불허 전량 재승인 | FULFILLING | 해당 회차 예약 증가 |
| FULFILLING | 출고 지시가 전혀 없고 전체 취소 가능 | CANCELLED | 유효 예약 전량 해제 |
| FULFILLING | 잔량·예약·운송·차이·출고 작업 모두 종결 | COMPLETED | 종결 시 별도 자동 조정 없음 |

재고 부족, 권한 부족, 오래된 버전, 유효하지 않은 수량은 상태 전이가 아니다. 업무 데이터는 변경하지 않고 명시적 오류를 반환한다.

REJECTED·CANCELLED·COMPLETED는 초기 버전에서 재개하지 않는다. FULFILLING에서 전체 반려는 허용하지 않으며 미충족 잔량을 사유와 함께 종결한다. 하나라도 출고 지시가 생성된 요청의 전체 취소는 후속 출고 취소 유스케이스를 따른다.

요청의 수명주기는 replenishment가 명령 처리 시 저장한다. 부분 승인·부분 출고·부분 입고 등 진행 표시는 하위 수량에서 계산한다. 다른 모듈의 변경으로 완료 가능해질 때도 replenishment의 완료 판정 기능을 호출하며 외부 모듈이 상태를 직접 갱신하지 않는다.

### 2.2 예약의 상태

한 예약은 일부 출고·일부 해제가 가능하므로 상태 enum 하나로 수량을 대체하지 않는다.

```text
예약 생성량 = 유효 잔량 + 출고 소비 누계 + 해제 누계
```

- 유효 잔량이 양수면 ACTIVE다.
- 유효 잔량이 0이면 CLOSED이며 소비·해제 내역으로 종료 이유를 확인한다.
- 회차·요청 항목별 예약 식별자를 갖고 부분 소비·해제는 별도 변동 기록으로 남긴다.
- 피킹 부족 해제 후 추가 승인하면 기존 예약을 되살리지 않고 새 회차·예약을 만든다.

## 3. 수량 불변식

모든 값은 낱개 단위의 0 이상 정수다. 요청 수량과 각 회차의 총 승인 수량은 양수여야 한다.

### 3.1 거점·SKU 재고

```text
정상 재고 N >= 0
보류 재고 H >= 0
유효 예약 합계 R >= 0
가용 수량 A = N - R >= 0
```

예약 수량을 잔액 행에 집계해 저장한다면 같은 트랜잭션에서 예약 상세·변동 기록과 함께 변경한다. 집계 수량과 상세 유효 잔량의 합이 같아야 하며 대사 테스트로 검증한다. SQL CHECK만으로 다른 행 합계까지 보장한다고 간주하지 않는다.

### 3.2 요청 항목의 이행

```text
요청 수량 Q = 열린 미배정 잔량 O + 유효 예약 Rq
            + 출고 누계 S + 미충족 종결 수량 C
```

- 승인 a: O에서 a를 빼고 Rq에 a를 더한다.
- 출고 s: Rq에서 s를 빼고 S에 s를 더한다.
- 피킹 부족 해제 x: Rq에서 x를 빼고 O에 x를 더한다.
- 잔량 종결 c: O에서 c를 빼고 C에 c를 더하며 사유를 남긴다.
- 출고 전 전체 취소: Rq를 해제하고 O와 함께 C로 이동하며 취소를 사유로 기록한다.

누적 승인량은 이행 현황의 보존식에 사용하지 않는다. 예를 들어 7장 승인 후 2장 부족 해제, 2장 재승인이면 승인 이력 합계는 9장이지만 요청은 여전히 7장이다.

### 3.3 출고 이후의 경계

```text
출고 누계 S = 정상 입고 G + 파손 입고 D
            + 운송 중 미해결 T + 승인된 운송 손실 L
```

이는 출고 문서와 일치하는 SKU의 정상적인 수량 정산 기준이다. 과다 입고·예상 외 SKU는 이 식을 깨면서 강제로 맞추지 않고 별도 차이 건과 출처 확인 후 조정한다. 상세 처리 절차는 입고 설계에서 확정한다.

COMPLETED는 모든 항목의 O·Rq·T가 0이고 미해결 차이 및 진행 중 출고 작업이 없을 때 가능하다. 전량 충족 여부, 파손·손실 여부는 별도로 표시한다. 취소·반려된 미출고 요청은 각 수명주기 상태로 종료한다.

## 4. 승인 명령 계약

HTTP 경로는 후속 API 명세에서 확정한다. 논리적인 명령 입력은 다음과 같다.

| 필드 | 규칙 |
|---|---|
| requestId | 대상 요청 |
| expectedVersion | 사용자가 조회한 요청 버전 |
| idempotencyKey | 동일 승인 시도의 재전송 식별자 |
| lines | 요청 항목 ID와 이번 회차 승인 수량; 모든 요청 항목을 명시 |
| reason | 부분 승인 시 사유 필수 |

승인자 ID·권한·소속은 인증 컨텍스트에서 얻는다. 클라이언트가 전달한 사용자 ID를 신뢰하지 않는다.

부분 이행 불허면 모든 항목을 전체 요청 수량대로 승인해야 한다. 후속 출고 기능의 전량 재승인은 부족 지시의 취소 확정 후 출고 누계와 유효 예약이 모두 0일 때만 허용한다. 전체 취소 진행 중에는 어떤 추가 승인도 허용하지 않는다. 부분 이행 허용이면 항목별 승인 수량은 열린 미배정 잔량을 초과할 수 없다. 제출 당시와 다른 SKU, 중복 항목, 누락 항목, 음수, 전체 0을 거절한다.

성공 결과는 승인 회차 ID, 요청 ID, 반영된 버전, 항목별 예약 ID·수량을 포함한다. 재고 부족 응답의 가용 수량은 실패 당시 관측값이며 이후 확보를 보장하지 않는다.

## 5. 승인 트랜잭션

초기 선택은 READ COMMITTED와 명시적인 요청 행 잠금, 재고 조건부 갱신이다. 아래 SQL은 논리 예시이며 실제 테이블명은 ERD에서 정한다.

1. 트랜잭션을 시작하고 승인 권한과 거점 범위를 확인한다.
2. 요청 행을 FOR UPDATE로 잠근다. 같은 요청의 승인·취소·잔량 변경·출고 지시 생성도 같은 행을 먼저 잠근다.
3. 같은 명령 키의 성공 기록을 확인한다. 동일 본문이면 저장된 성공 결과를 반환한다. 다른 본문이면 충돌로 거절한다. 현재 권한 확인은 재전송에도 적용한다.
4. 신규 명령이면 expectedVersion과 상태·항목·부분 이행 정책을 검증한다.
5. 승인 회차와 상세를 저장하고 JPA를 flush한다. 양수 승인 상세 ID를 재고 모듈에 전달한다. 예약할 재고 키를 (거점 ID, SKU ID) 오름차순으로 정렬한다.
6. 각 키에 대해 가용 수량 조건을 포함해 예약 집계를 갱신한다.

```sql
UPDATE inventory_balance
SET reserved_qty = reserved_qty + :qty
WHERE location_id = :locationId
  AND sku_id = :skuId
  AND normal_qty - reserved_qty >= :qty;
```

7. 갱신 행 수가 1이 아니면 부족 또는 잔액 행 부재로 판단하고 전체 롤백한다. 초기 버전에서 잔액 행 부재는 가용 0으로 취급한다.
8. 승인 상세를 참조하는 예약·예약 변동·재고 원장을 저장하고 요청 항목의 열린 잔량을 감소시킨다.
9. 요청 수명주기·버전·승인 이력과 명령 키·본문 해시·성공 응답을 저장한다.
10. 전부 커밋한 뒤 응답한다. 중간 단계 실패는 앞서 성공한 다른 SKU 예약까지 롤백한다.

예약 성공 후 요청 저장이 실패하는 경우도 동일하게 롤백한다. WMS 호출이나 Outbox 생성은 이 명령에 포함하지 않는다.

부분 허용 요청도 임의로 성공한 SKU만 남기지 않는다. 지정 승인량이 부족하면 전부 롤백하며, 담당자가 수량을 변경한 새 명령을 제출한다.

## 6. 동시 처리와 잠금 순서

- 동일 요청 명령은 요청 행 잠금으로 직렬화한다.
- 서로 다른 요청이 같은 SKU를 예약하면 재고 갱신이 경합하며 가용 수량 조건으로 초과 예약을 방지한다.
- 공통 잠금 순서는 요청 ID 오름차순 → 하위 업무 문서 ID 오름차순 → 재고 키 오름차순이다. 예약 상세는 해당 재고 키 아래에서 일관된 순서로 처리한다.
- 출고·입고 등 후속 명령도 이 순서를 준수해야 한다. 여러 요청을 묶는 기능은 초기 범위에 두지 않는다.
- 다른 모듈의 재고 변경 경로도 정상 재고가 유효 예약보다 작아지지 않게 검사한다. 영향받는 예약이 있으면 조사 보류 절차로 전환한다.
- 교착·직렬화 실패는 트랜잭션 밖에서 동일 명령으로 전체 재시도한다. 초안 정책은 최초 1회 + 재시도 최대 2회이며 짧은 지터를 둔다. 잠금 대기 한도는 실제 환경에서 정하고 무한 대기하지 않는다.
- 재고 부족·권한 오류·오래된 버전·본문 충돌은 자동 재시도하지 않는다.

## 7. 멱등성과 실패 결과

- 키 범위는 (명령 종류, 요청 ID, 인증 사용자 ID, idempotencyKey)이며 DB 유니크 제약으로 보호한다.
- 해시는 expectedVersion과 정렬된 승인 항목 등 의미 있는 전체 입력을 정규화한 값으로 계산한다. 재전송 시 항목 순서만 다른 것은 동일 입력이다.
- 성공 결과는 업무 변경과 같은 트랜잭션에 저장한다. 커밋 후 응답이 유실돼도 같은 키로 결과를 복원한다.
- 초안에서는 성공 키와 응답을 자동 만료하지 않는다. 개인정보·용량에 따른 보관 정책은 운영 확장 시 별도 결정한다.
- 실패는 예약·승인 회차를 남기지 않으며 키를 소비하지 않는다. 실패 응답은 캐시하지 않는다. 같은 입력을 다시 제출하면 현재 조건으로 재평가된다.
- 실패 시도는 구조화 로그로 남긴다. 업무 승인 감사 기록과 실패 시도 로그를 구분한다.

| 상황 | 결과 |
|---|---|
| 같은 키·같은 본문, 이전 성공 | 기존 성공 결과 반환, 버전·예약 변경 없음 |
| 같은 키·다른 본문, 이전 성공 | IDEMPOTENCY_CONFLICT |
| 다른 키로 중복 승인, 오래된 버전 | VERSION_CONFLICT |
| 이미 취소·반려·완료된 요청 | INVALID_STATE |
| 승인 지정량보다 재고 부족 | INSUFFICIENT_STOCK, 전체 롤백 |
| 권한 부족 | FORBIDDEN, 업무 변경 없음 |
| 잠금 실패 재시도 소진 | 일시 충돌 오류, 새로 조회 또는 동일 명령 재시도 안내 |

## 8. 출고 전 취소와의 경합

취소도 같은 요청 행을 먼저 잠근다. 출고 지시가 전혀 없음을 확인한 뒤 유효 예약 해제·미충족 종결·취소 상태·이력·멱등성 결과를 함께 커밋한다.

- 승인이 먼저 커밋되면 취소는 최신 버전과 재고를 기준으로 다시 판단한다. 오래된 화면 버전이면 충돌을 반환한다.
- 취소가 먼저 커밋되면 승인은 CANCELLED 상태 때문에 실패한다.
- 출고 지시 생성이 먼저 커밋되면 즉시 취소 경로는 실패하고 WMS 취소 확인 경로로 진행한다.
- 단순 상태 조회 후 나중에 예약을 해제하는 방식은 사용하지 않는다.

| AR-02 | 정상 18·기존 예약 8·보류 4; A 7·B 6 동시 승인 | 신규 합계 10 이하; 전체 수량 승인 요청 둘 다 성공하지 않음 |
| AR-03 | AR-02에서 A 커밋 후 B 승인 | A 7 성공, B 6 실패, 기존 예약 8 유지 |
| AR-04 | 두 SKU 중 두 번째 부족 | 이미 flush한 승인 기본·상세와 첫 SKU 예약·원장·요청 변경 모두 롤백. 기존 잔액 유지 |
| AR-05 | 재고 갱신 후 요청 저장 실패 주입 | 잔액·예약 상세·이력·명령 키 모두 롤백 |
| AR-06 | 같은 승인 키·본문 동시 제출 | 한 회차만 생성, 두 호출은 같은 결과 |
| AR-07 | 커밋 후 HTTP 응답 유실, 같은 키 재전송 | 추가 예약 없이 기존 결과 반환 |
| AR-08 | 성공한 키의 본문만 변경 | 충돌, 기존 결과 불변 |
| AR-09 | 승인·취소 동시 요청 | 유효한 순서 하나로 처리, 취소 후 예약 잔존 없음 |
| AR-10 | 요청 7·최초 승인 5·추가 승인 2 | 별도 회차 2개, 총 유효 예약 7, 잔량 0 |
| AR-11 | 부분 불허인데 5/7 승인 또는 다른 사이즈 지정 | 입력 거절, 업무 변경 없음 |
| AR-12 | 7 예약 → 2 부족 해제·보류 → 5 출고 | 열린 잔량 2, 유효 예약 0, 출고 5; 부족 2는 가용에 포함 안 됨 |
| AR-13 | 역순 SKU 입력으로 여러 요청 동시 승인 | 내부 정렬로 일관된 잠금, 재시도 포함 최종 수량 일치 |
| AR-14 | 다른 매장 사용자·승인 권한 없는 사용자 | 권한 거절, 업무 데이터 불변 |
| AR-15 | 같은 사용자가 같은 제출 키·본문으로 동시에 신청 | 요청·제출 이력 각각 한 건, 동일 201 본문 및 Location |

AR-02는 실제 동시 시작으로 불변식을 검증하고 AR-03은 순서를 통제하여 결과를 검증한다. Thread.sleep으로 특정 승자를 가정하지 않는다. 모든 DB 정합성 검증은 Testcontainers PostgreSQL에서 수행하며 집계·상세·원장을 함께 비교한다.

## 10. 후속 ERD 및 API 명세 입력

- 요청·항목·버전·승인 회차·회차별 항목
- 재고 잔액·예약·예약 변동·재고 이동 원장
- 명령 멱등성 기록·성공 응답·승인 감사 이력
- 유니크 키, 수량 CHECK, 외래 키, 잠금 조회 인덱스
- 출고 지시에 배정한 예약 수량과 미지시 예약의 구분
- 박스별 입고·차이 조사 및 외부 메시지 계약

이 문서는 승인·예약 설계 초안이며 테스트가 통과했다는 의미는 아니다. 초기화 후 위 인수 사례를 구현하여 설계의 타당성을 검증한다.

## 11. 기술 근거

[PostgreSQL 공식 문서: 트랜잭션 격리](https://www.postgresql.org/docs/18/transaction-iso.html)의 READ COMMITTED 설명을 참고했다. 경합한 UPDATE는 앞선 변경을 기다린 뒤 갱신된 행에 WHERE 조건을 다시 평가한다. 이 특성을 사용해 단일 재고 행의 가용 수량 조건을 검사하되, 여러 SKU와 요청 변경의 원자성은 전체 트랜잭션으로 보장한다. 참고 문서 버전은 PostgreSQL 제품 버전 확정을 의미하지 않는다.
