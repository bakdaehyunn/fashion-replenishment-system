# 운송 손실 확정 구현 명세

관련 문서 [OpenAPI](openapi.yaml) · [부족 검수와 추가 입고](receiving-shortage-flow.md) · [보충 이행 상태](fulfillment-state-design.md)

## 권한과 업무 흐름

출고 6장 중 정상 5장만 도착하면 부족 1장이 조사 대상으로 남는다. 조사 결과를 확인한 출발 창고의 활성 소속 물류 운영 담당자가 손실 수량·사유·근거 식별자를 입력해 확정한다. 이 단계에서는 기존 LOGISTICS_OPERATOR 역할을 사용한다. 매장 직원은 소속 매장의 결과를 조회하고 추가 도착을 등록할 수 있다. 서버는 권한과 요청·출고·박스·부족 건의 소속 관계를 확인한다.

근거 식별자는 운송사 조사 건 번호처럼 사후 추적할 수 있는 문자열이다. 사유와 근거는 공백을 제거한 뒤 각각 1~500자, 1~200자여야 한다. 손실 수량은 1 이상이며 미해결 잔량 이하여야 한다. 일부만 확정하면 부족 건은 OPEN을 유지한다.

## API와 화면

기존 부족 건 경로에 POST `/losses`를 추가한다. 입력은 `expectedVersion`, `lostQty`, `reason`, `evidenceReference`다. 성공 시 201과 `lossId`, `confirmedAt`, 갱신된 요청 버전·상태·박스 정보를 반환한다.

박스와 출고 상세의 각 SKU에 `lostQty`를 표시한다. 전량 정산 후 요청은 COMPLETED가 되고, 출고 상세에서 운송 손실 수량을 함께 보여준다. 승인 ID·사유·근거는 원장에 보존한다.

- 명령 종류는 TRANSIT_LOSS다. 해시에는 부족 건 ID, 기대 버전, 손실 수량과 정규화한 사유·근거를 포함한다.
- 현재 접근 권한을 확인한 뒤 성공 키를 재생한다. 입력이 다르면 IDEMPOTENCY_CONFLICT다.
- 새 명령은 버전을 먼저 검사한다. 오래된 버전은 VERSION_CONFLICT, 최신 버전이라도 종결된 부족 건이나 초과 수량은 RECEIPT_SHORTAGE_CONFLICT다. 범위를 벗어난 계정은 403, 경로에 속하지 않는 부족 건은 404다.

## Flyway V5와 수량 정산

`transit_loss`를 추가한다. ID, 부족 건 FK, 양수 손실 수량, 확정자 FK, 확정 시각, 사유, 근거 식별자를 저장한다. 이 추가 전용 테이블이 운송 손실 원장이다. 매장과 창고의 재고 잔액이나 거점 원장에 증감 항목을 만들지 않는다. 부족 건 FK에 조회 인덱스를 둔다.

`receiving_line_totals`에 SKU별 손실 합계를 추가한다. 추가 입고와 손실은 각각 따로 집계한 뒤 결합한다. 운송 중 미해결 수량은 **출고 − 정상 입고 누계 − 운송 손실 누계**다. 원본 검수와 추가 입고 기록은 그대로 보존한다.

요청 → 박스 → 부족 건 순으로 잠근다. 추가 입고와 손실 확정은 같은 요청 잠금과 잔량 조건을 공유한다. 운송 손실 원장, 부족 잔량 차감, 요청 상태·버전, 업무 이력과 멱등성 응답을 한 트랜잭션에 기록한다. 모든 박스 검수가 확정되고 미해결 차이·운송 중·예약·열린 잔량이 0일 때만 완료한다.

## 인수 기준

| 사례 | 기대 결과 |
|---|---|
| 출고 6 → 입고 5 → 손실 1 | 창고와 매장 재고 유지, 매장 정상 5, 운송 중 0, 손실 1, 부족 RESOLVED, 요청 COMPLETED |
| 같은 부족 1에 추가 입고와 손실 확정 경합 | 판단 한 건만 반영. 입고가 이기면 매장 정상 6·손실 0, 손실이 이기면 매장 정상 5·손실 1 |
| 동일한 손실 명령 재전송 | 최초 201과 같은 손실 ID 반환, 원장 추가 없음 |
| 권한 없음·초과 수량·근거 누락 | 각각 403·409·400, 업무 데이터 변경 없음 |
| 원장 저장 실패 | 부족 잔량과 요청 상태·버전 유지, 성공 키 기록 없음 |
