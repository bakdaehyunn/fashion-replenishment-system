# 보충 이행 세부 상태 및 전체 상태 판정 명세 v0.1

WMS의 상황 지정·랜덤 실행·업무 API·이벤트 재현 계약은 [WMS 시뮬레이터 명세](wms-simulator-spec.md)를 따른다. 데모 발송 보류와 취소 선접수 처리는 해당 명세에서 구체화한다.

관련 문서: [요구사항](requirements.md) · [테이블](table-design.md) · [모듈](module-design.md) · [승인·예약](approval-reservation-design.md)

## 1. 목적과 설계 상태

출고·검수·수량 차이의 상태 및 수량으로 보충 요청 전체의 상태와 진행 사유를 설명한다. 프로젝트 운영 가정이며 실제 기업 정책이 아니다. 구현·실행 검증 전 설계 명세다.

요청 메인에는 수명주기를 저장하고, 부분 출고·검수 대기 등의 진행 사유는 하위 사실에서 계산한다. 모든 하위 상태를 하나의 순번으로 비교하거나 가장 뒤의 상태를 요청 상태로 복사하지 않는다. 여러 출고·박스·조사가 동시에 다른 단계에 있을 수 있다.

## 2. 상태 소유권

| 대상 | 현재 상태 저장 | 변경 이력 | 소유 모듈 |
|---|---|---|---|
| 보충 요청 | replenishment_request.status | request_status_history | replenishment |
| 출고 지시 | outbound_order.status | outbound_status_history | fulfillment |
| 출고 취소 | outbound_order.cancellation_status | outbound_status_history의 CANCELLATION 축 | fulfillment |
| 박스 | outbound_carton.status | 확정 출고 기록 및 출고 지시 이력 | fulfillment |
| 입고 검수 | receiving_inspection.status | receiving_status_history | receiving |
| 수량 차이 | inventory_discrepancy.status | discrepancy_history | receiving |
| 메시지 전달 | outbox_message.status | integration_attempt | integration |

현재 상태·수량·필수 이력은 동일 트랜잭션으로 변경한다. 메시지 전달 완료, 창고 접수, 실제 출고는 별개 사실이다. 다른 모듈은 공개 명령을 통해 소유 모듈에 변경을 요청한다.

## 3. 출고 지시 생성 조건

- 승인된 FULFILLING 요청이고 출발 창고와 목적 매장이 유효하다.
- 지시 수량은 양수이고 해당 요청의 동일 SKU 유효 예약에서 배정한다.
- 기존 출고 지시의 미출고·미해제 배정량을 제외한 예약 잔량만 사용한다.
- 부분 이행 불허 요청은 전체 요청의 미이행 수량을 확보한 상태에서 지시한다.
- 하나의 출고 지시는 하나의 요청만 대상으로 한다.
- 출고 지시·항목·예약 배정·초기 상태 이력·Outbox 메시지를 함께 저장한다.
- 지시 생성은 예약 배정이며 실물 차감이나 예약 소비가 아니다.

## 4. 출고 업무 상태

| 상태 | 의미 | 종료 여부 |
|---|---|---|
| DISPATCH_PENDING | 로컬 지시 생성, WMS 접수 아직 확인 안 됨 | 아니오 |
| ACCEPTANCE_UNKNOWN | 전송했으나 접수 여부 미확인 | 아니오 |
| ACCEPTED | WMS가 동일 지시 ID의 접수를 확인 | 아니오 |
| WORKING | 창고 작업 시작 확인 | 아니오 |
| PICKING_EXCEPTION | 최종 피킹 결과 부족, 재할당·부분 출고 판단 필요 | 아니오 |
| READY_TO_SHIP | 해당 출고 회차의 확정 수량 확보·포장 완료 | 아니오 |
| SHIPPED | 회차의 실제 출고와 미출고 잔량 처리가 확정됨 | 예 |
| CANCELLED | WMS가 미출고 취소를 확정함 | 예 |
| REJECTED | WMS가 작업 미수행·지시 거절을 확정함 | 예 |

SHIPPED는 보충 요청 전량 출고를 뜻하지 않는다. 일부만 출고한 회차도 미출고 지시 잔량을 해제·정산한 뒤 SHIPPED가 된다. 회차의 출고 박스는 하나 이상의 박스일 수 있지만, 초기 WMS 계약에서는 회차별 최종 출고 확정 이벤트로 함께 처리한다. 순차적인 부분 박스 발송은 여러 출고 지시로 나눈다.

### 4.1 전이 조건과 재고 영향

| 현재 | 입력·조건 | 이후 | 수량·처리 |
|---|---|---|---|
| DISPATCH_PENDING | 접수 확인 | ACCEPTED | 변동 없음 |
| DISPATCH_PENDING | 타임아웃·응답 판독 불가 | ACCEPTANCE_UNKNOWN | 예약 유지 |
| ACCEPTANCE_UNKNOWN | 결과 조회 또는 재전송으로 접수 확인 | ACCEPTED | 새 지시 생성 금지 |
| DISPATCH_PENDING/ACCEPTANCE_UNKNOWN | 작업 미수행이 보장된 명시적 거절 | REJECTED | 배정 해제, 예약 유지 |
| ACCEPTED | 작업 시작 확인 | WORKING | 변동 없음 |
| ACCEPTED/WORKING | 최종 피킹 부족 확인 | PICKING_EXCEPTION | 확정 부족분 예약 해제·조사 보류, 요청 잔량 복원 |
| ACCEPTED/WORKING | 전량 확보·포장 확인 | READY_TO_SHIP | 예약 유지, 창고 실물 차감 없음 |
| PICKING_EXCEPTION | 부분 허용·담당자 부분 출고 확정·포장 완료 | READY_TO_SHIP | 확보분 유지, 부족 지시분 해제 확정 |
| READY_TO_SHIP | 최종 출고 확인 및 수량 일치 | SHIPPED | 창고 정상·예약 차감, 운송 중 증가 |
| 미종료 상태 | WMS 취소 확정, 출고 없음 | CANCELLED | 배정·관련 예약 해제, 요청 열린 잔량 증가 |

대체 위치 확인은 최종 부족 보고 전에 끝낸다. 최종 보고 뒤 확보한 잔량은 새 승인 회차·예약·출고 지시로 처리한다. 부분 불허 요청은 부족한 지시에서 출고하지 않는다. 기존 지시를 WMS에서 취소해 남은 예약도 해제한 후, 전량을 새 승인 회차에서 확보하고 새 지시를 생성한다.

거절은 요청 취소가 아니다. 초기 정책상 예약을 유지하여 새 지시를 생성할 수 있다. 예약도 해제하려면 별도 취소·잔량 처리 명령을 사용한다. 취소된 출고 지시의 예약 해제도 요청 자체를 자동 취소시키지 않는다.

## 5. 취소 축과 경합

| cancellation_status | 의미 |
|---|---|
| NONE | 취소 요청 없음 |
| REQUESTED | 취소 명령 전달·확인 진행 중 |
| CONFIRMED | 미출고 취소 확정 |
| REJECTED | 창고가 취소 불가 확정 또는 최종 출고 사실 확인 |

- 취소 REQUESTED 동안에도 실제 작업·출고 상태를 별도로 유지한다.
- 초기 정책은 출고 지시 생성 이후 항상 WMS 확인을 거친다. 전송 대기 메시지라는 이유만으로 로컬에서 안전한 미접수를 가정하지 않는다.
- 전체 취소는 요청 행 잠금 아래 전체 취소 의도를 기록하고 기존 지시에 대한 취소 명령을 등록한다. 처리 중에는 추가 승인과 새 출고 지시를 차단한다. 모든 지시가 미출고로 종결되면 전체 취소를 확정한다. 출고가 확인되면 전체 취소 의도는 거절로 종결하고 남은 미출고량만 사유와 함께 종결한다.
- 취소 요청과 Outbox 기록은 함께 저장한다. 응답 타임아웃에는 REQUESTED와 예약을 유지한다.
- 취소 확정 시 출고 status=CANCELLED, cancellation_status=CONFIRMED 및 예약·배정 해제를 함께 반영한다.
- 요청 중 최종 출고가 확인되면 status=SHIPPED, cancellation_status=REJECTED로 처리하고 출고 수량을 반영한다.
- WMS는 동일 지시의 취소 확정과 출고 확정을 동시에 유효한 결과로 보내지 않는 계약이어야 한다. 모순된 확정 이벤트는 새 재고 변경 없이 충돌 보류·조회 대상으로 남긴다.
- 취소 불가 응답만 받았다고 출고 완료로 만들지 않는다. 실제 작업 상태 확인을 계속한다.
- 이미 전량 출고된 지시에는 취소를 접수하지 않는다. 반품은 후속 범위다.
- 모든 미출고 지시 취소 확인, 예약·열린 잔량 종결, 미확인 메시지 결과 정산 후 요청 전체 취소를 확정한다. 어느 지시든 출고됐으면 전체 CANCELLED로 만들지 않고 남은 잔량만 종결한다.

## 6. 피킹 부족과 원장 반영

예: 요청 7, 예약 7, 실제 확보 5, 대체 위치 확보 실패 2.

1. 업무 요청·출고 지시를 잠그고 새 피킹 revision인지 확인한다.
2. 부족 2의 예약 및 배정을 해제하고 요청 열린 잔량 2를 복원한다.
3. 창고 정상 -2, 보류 +2로 전환한다. 다른 예약을 침범하면 자동 반영을 중단하고 조사 대상으로 남긴다.
4. 부족 차이 건을 생성하고 출고는 PICKING_EXCEPTION으로 둔다.
5. 부분 허용이면 담당자가 5장 출고를 확정하고, 포장 후 READY_TO_SHIP으로 진행한다.
6. 5장 출고 확정 시 정상 -5, 예약 -5, 요청 출고 +5를 반영한다.

확보 위치 부족 통지만으로 센터 전체 손실을 확정하지 않는다. WMS 대체 위치 확인 후 최종 부족 결과를 근거로 보류한다. 실사 결과에 따라 정상 복원 또는 승인된 손실 조정을 별도 원장에 기록한다.

## 7. 박스 및 입고 검수

박스는 PACKED → SHIPPED다. 박스 합계와 회차 출고 수량, SKU, 배정 수량을 검증한 뒤 출고 확정한다. 동일 박스 중복 출고는 반영하지 않는다.

검수 문서의 저장 상태는 DRAFT → CONFIRMED이며 CONFIRMED는 원본 수정 불가다. 화면의 박스 진행 상태는 다음처럼 계산한다.

| 화면 표시 | 조건 |
|---|---|
| 검수 대기 | SHIPPED 박스에 최초 검수 문서 없음 |
| 검수 중 | 최초 검수 DRAFT 존재 |
| 검수 확정 | 최초 검수 CONFIRMED 존재 |

검수 대기를 저장하기 위해 빈 검수 문서를 미리 만들 필요는 없다. 정상·파손 수량 합계가 출고보다 적어도 부족 차이 건을 생성하며 검수를 확정할 수 있다. 검수 확정은 수량 차이 해결을 뜻하지 않는다.

### 7.1 확정 시 수량 처리

- 정상 수량: 운송 중 감소, 매장 정상 재고 증가.
- 파손 수량: 운송 중 감소, 매장 보류 재고 증가, 파손 조사 건 생성.
- 부족 수량: 운송 중 미해결로 유지하고 부족 조사 건 생성.
- 과다 수량·예상 외 SKU: 별도 관측·보류 입고 및 차이 근거를 기록하고 예상 출고 수량 정산과 분리한다. 정상 재고에 자동 반영하거나 운송 중을 음수로 만들지 않는다.
- 초과·예상 외 항목의 출처 확인 전에는 관련 요청을 완료하지 않는다.
- 검수 확정·원장·요청 진행 판정·차이 건·멱등성 결과는 함께 커밋한다.

운송 잔량은 박스 상세별 출고량 − 유효 정상·파손 입고 − 승인 운송 손실이다. 추가 입고와 손실 정산은 동일 요청과 박스 상세를 잠그고 최신 잔량을 검증한다. 미확인 1장에 추가 입고와 손실 승인이 경합하면 한 쪽만 반영된다. 초과·예상 외 관측량은 이 계산에서 제외한다.

추가 도착은 ADDITIONAL 검수로 남겨 해당 부족 건을 해결한다. 추가 수량은 아직 미해결인 수량을 초과해 정산하지 않는다. 검수 오류는 CORRECTION으로 원본 역분개 및 대체 검수를 함께 반영한다. 이미 추가 검수·손실·차이 정산 등 후속 의존이 생긴 원본은 초기 버전에서 보정을 거절하고 별도 담당자 확인 대상으로 둔다. 후속 문서까지 자동 연쇄 취소하지 않는다.

## 8. 수량 차이 조사

| 현재 | 조건·작업 | 이후 | 재고 영향 |
|---|---|---|---|
| OPEN | 담당자 배정 및 조사 시작 | INVESTIGATING | 없음 |
| OPEN/INVESTIGATING | 조사 메모·일부 해결 | 현재 유지 | 근거 있는 해결 수량만 반영 |
| OPEN/INVESTIGATING | 전체 수량 해결 및 필수 근거 확인 | RESOLVED | 조정 필요 시 같은 트랜잭션 |

| 유형 | 해결 예 | 수량 처리 |
|---|---|---|
| PICK_SHORTAGE | 재실사로 발견 | 창고 보류 → 정상; 부족 요청의 재예약은 별도 승인 |
| PICK_SHORTAGE | 실사 후 손실 확정 | 창고 보류 차감 및 손실 원장 |
| RECEIPT_SHORTAGE | 추가 도착 검수 | 운송 중 → 매장 정상/보류 |
| RECEIPT_SHORTAGE | 운송 손실 승인 | 운송 중 미해결 → 운송 손실 |
| DAMAGE | 재검수 정상 판정 | 매장 보류 → 정상 |
| DAMAGE | 폐기·손실 승인 | 매장 보류 차감 및 손실 원장 |
| OVERAGE/UNEXPECTED_SKU | 출처·소유 확인 후 재고 승인 | 보류 → 정상 등 승인된 조정; 확인 전 미해결 |

해결은 단순 상태 변경이 아니다. 해결 수량·근거·담당자·연결 원장 또는 검수 기록이 있어야 한다. 같은 수량을 추가 입고와 손실로 중복 정산하지 않는다. 미해결 조사 건은 완료를 막되, 취소 후 남은 창고 실사 조사처럼 요청 수명주기가 이미 종료된 업무는 별도 조사 큐에서 계속 추적한다.

## 9. 보충 요청 전체 상태 판정

| 전체 상태 | 진입 조건 |
|---|---|
| DRAFT | 작성 중 |
| SUBMITTED | 제출됐고 유효 승인 이전 |
| REJECTED | 승인 전 명시적 반려 |
| FULFILLING | 하나 이상의 승인 회차 확정, 완료·취소 조건 미충족 |
| CANCELLED | 출고 누계 0, 전체 취소 명령, 지시 취소·결과 확인 완료, 예약·열린 잔량 전량 종결 |
| COMPLETED | 아래 완료 조건 모두 만족 |

### 9.1 완료 조건: 전부 AND

- 현재 요청은 FULFILLING이다. 반려·취소·초안에 완료 판정을 적용하지 않는다.
- 모든 요청 항목의 열린 미배정 잔량 O=0.
- 모든 요청 항목의 유효 예약 Rq=0.
- 모든 출고 항목의 운송 중 미해결 수량 T=0.
- 모든 출고 지시는 SHIPPED/CANCELLED/REJECTED 중 하나로 종결됐다.
- 출고된 모든 박스의 최초 검수가 확정됐다.
- 미해결 차이 건과 진행 중 보정 문서가 없다.
- 취소 결과 미확인 및 업무 결과에 영향을 줄 수 있는 미처리·충돌 이벤트가 없다.
- 수량 보존식·집계 대사가 일치한다.

승인된 요청이 재고 부족 등으로 출고 없이 잔량 전부 종결됐다면 COMPLETED가 될 수 있다. 표시 결과는 CLOSED_UNFULFILLED다. 전체 취소 명령으로 종료한 CANCELLED와 구분한다.

### 9.2 수량 보존식과 결과 구분

```text
요청 Q = 열린 잔량 O + 유효 예약 Rq + 출고 S + 미충족 종결 C
출고 S = 정상 입고 G + 파손 입고 D + 운송 중 미해결 T + 운송 손실 L
```

과다·예상 외 입고는 위 식과 별도 정산한다. 파손 D는 입고 당시 사실로 유지하며 이후 정상 전환·폐기 결과는 원장과 조사 해결 내역으로 표시한다. 문서 보정 시에는 유효 검수 기준으로 재집계한다.

완료 상태와 함께 수량에서 다음 결과 플래그를 계산한다. 플래그는 복수일 수 있다.

- FULLY_SHIPPED: S=Q.
- CLOSED_UNFULFILLED: C>0.
- DAMAGE_RECORDED: 유효 파손 입고 D>0.
- TRANSIT_LOSS_RECORDED: L>0.

COMPLETED만으로 전량 정상 입고를 주장하지 않는다.

## 10. 진행 사유 계산 및 화면

FULFILLING 요청은 모든 해당 사유를 badges로 반환한다. 주요 사유는 아래 우선순위로 하나를 고르지만 다른 사유·수량을 숨기지 않는다.

| 우선순위 | 사유 | 조건 |
|---|---|---|
| 1 | 연동 결과 확인 필요 | 접수 미확인·충돌·선행 이벤트 누락·수동 확인 대상 존재 |
| 2 | 취소 확인 중 | REQUESTED 취소 존재 |
| 3 | 수량 차이 조사 중 | OPEN/INVESTIGATING 조사 존재 |
| 4 | 피킹 부족 처리 중 | PICKING_EXCEPTION 존재 |
| 5 | 입고 검수 중 | 미확정 최초 검수 DRAFT 존재 |
| 6 | 입고 확인 대기 | 출고 박스 중 최초 검수 미확정 존재 |
| 7 | 창고 작업 중 | ACCEPTED/WORKING/READY_TO_SHIP 존재 |
| 8 | 출고 전달 대기 | DISPATCH_PENDING 존재 |
| 9 | 추가 이행 대기 | 열린 잔량 O>0 |
| 10 | 출고 지시 대기 | 미배정 유효 예약 존재 |

아무 조건에도 해당하지 않는데 완료할 수 없으면 정상적인 새 상태로 숨기지 않고 정합성 확인 필요로 표시·기록한다. 부분 승인·부분 출고·부분 검수는 위 사유와 별도의 수량 배지다.

예시:

```text
이행 중 · 수량 차이 조사 중
요청 12 / 출고 12 / 정상 입고 10 / 파손 입고 1 / 미확인 1
차이: 파손 1 조사 중, 부족 1 조사 중
```

미확인 1과 조사 수량 2는 다른 개념이다. 파손은 이미 도착했으므로 운송 중에는 포함하지 않는다. 3개 박스 중 하나 검수, 하나 운송, 하나 준비 중이라면 각 건수와 사유를 함께 표시한다.

## 11. 원자성·이벤트 적용 규칙

- 상태·수량·원장·업무 이력·Inbox 처리 완료를 하나의 트랜잭션으로 반영한다.
- 기존 잠금 순서인 요청 → 하위 문서 → 재고 키 → 예약 상세를 준수한다.
- 변경 후 replenishment의 완료 판정 기능을 호출한다. 요청의 주요 사유는 저장된 enum 대신 조회 시 계산한다.
- 여러 테이블을 조합한 화면 조회는 하나의 일관된 읽기 스냅샷을 사용한다. 구현 시 단일 조회 또는 읽기 전용 REPEATABLE READ 트랜잭션 중 선택하고 검증한다.
- 동일 이벤트·동일 내용은 재반영하지 않는다. 같은 ID·다른 내용은 충돌로 보관한다.
- 선행 정보가 없는 출고 알림은 보류한다. 창고 확정 조회로 필요한 근거를 확보하거나 선행 이벤트 반영 후 재처리한다.
- 오래된 상태 이벤트로 회귀하지 않는다. 단, 아직 반영하지 않은 유효 재고 사실을 오래된 타임스탬프라는 이유로 버리지 않는다.
- 업무 처리 후 HTTP 응답 유실은 같은 명령·이벤트 ID로 결과를 복원한다.
- COMPLETED 후 중복 알림은 무시하되, 새 충돌·보정 요청은 자동으로 상태를 되돌리지 않는다. 초기 버전은 보정 거절·수동 조사 대상으로 기록하고 완료 후 보정 지원은 별도 설계한다.
