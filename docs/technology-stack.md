# 기술 스택 및 선택 근거

상태: 초기 기술 구성 합의. 정확한 제품·라이브러리 버전은 프로젝트 초기화 시 호환성을 확인하여 고정한다.

관련 문서: [요구사항 정의서](requirements.md)

## 1. 선택 원칙

- 업무 시나리오와 해결할 문제를 먼저 정의하고 기술을 선택한다.
- 트랜잭션, 동시성, 멱등성, 외부 연동 장애 복구와 추적 가능성을 핵심 구현 대상으로 삼는다.
- 프로젝트에서 검증한 경험과 실제 운영 경험을 구분하여 설명한다.
- 새로운 기술은 필요성을 설명하고 실패 상황까지 검증할 수 있을 때 도입한다.
- 초기 구조를 단순하게 유지하고, 규모 또는 요구사항 확장에 따라 추가 기술을 검토한다.

## 2. 초기 기술 구성

| 영역 | 선택 | 사용 목적 및 선택 이유 |
|---|---|---|
| 언어·런타임 | Java 25 | 사용자 선호를 반영하며 개발·CI·실행 환경의 toolchain을 동일하게 고정한다 |
| 백엔드 | Spring Boot · Spring MVC | 트랜잭션 중심 업무와 동기식 관계형 DB 접근을 구현한다 |
| 빌드 | Gradle Kotlin DSL | Java toolchain, 의존성, 테스트 및 빌드 작업을 관리한다 |
| 데이터베이스 | PostgreSQL | 제약조건, 트랜잭션, 조건부 갱신 및 행 잠금으로 상태와 수량 정합성을 보장한다 |
| 데이터 접근 | Spring Data JPA + JdbcClient | 일반 업무 엔티티는 JPA로 관리하고 재고 조건부 갱신·Outbox 등은 명시적 SQL로 구현한다 |
| 스키마 변경 | Flyway | DB 스키마 변경을 버전 관리하고 동일하게 재현한다 |
| 인증·인가 | Spring Security + 세션 | 사내 웹 로그인과 역할·소속 매장 단위 접근 제어를 구현한다 |
| WMS 연동 | RestClient · HTTP/JSON | 출고 지시·조회·취소 요청과 타임아웃·오류 처리를 구현한다 |
| 백그라운드 처리 | Spring Scheduling + DB Outbox | 발송 대기 메시지, 재시도 및 결과 미확인 작업의 확인을 수행한다 |
| 테스트 | JUnit + Testcontainers PostgreSQL | 실제 PostgreSQL에서 롤백·동시 승인·중복 처리·수량 보존을 검증한다 |
| 프론트엔드 | React · TypeScript · Vite | 요청·승인·검수·예외 처리용 업무 화면을 제공한다 |
| 로컬 실행 | Docker Compose | 애플리케이션·DB·WMS 시뮬레이터 실행 환경을 재현한다 |
| CI | GitHub Actions | 빌드와 자동 테스트를 실행한다 |

라이브러리의 정확한 버전, JDK 배포판, PostgreSQL 메이저 버전과 컨테이너 이미지는 초기화 시 선택하고 고정한다. Java 25를 기준으로 하며 임의로 상위 버전을 사용하지 않는다.

## 3. 애플리케이션 구조

단일 백엔드 애플리케이션 안에서 업무 책임별 모듈을 분리하고, 별도의 WMS 시뮬레이터와 HTTP로 연동한다.

```text
React 업무 화면
       │
Spring Boot 애플리케이션
 ├─ 상품·거점
 ├─ 보충 요청·승인
 ├─ 재고·예약
 ├─ 출고·WMS 연동
 ├─ 입고·수량 차이
 └─ 권한·감사 이력
       │
   PostgreSQL

Spring Boot ← HTTP/JSON → WMS 시뮬레이터
```

WMS 시뮬레이터는 정상 접수, 거절, 접수 후 응답 유실, 중복 알림, 순서 역전과 취소 경합을 재현한다. 실제 물류 운영 경험으로 표현하지 않는다.

## 4. 데이터 접근과 정합성

- 승인 상태 변경, 재고 예약, 관련 이력은 필요한 트랜잭션 경계에서 함께 반영한다.
- 일반적인 엔티티 조회·변경은 JPA를 기본으로 사용한다.
- 재고 확보 조건을 포함한 갱신과 작업 선점 등 SQL 제어가 필요한 부분은 JdbcClient를 사용한다.
- 같은 데이터에 JPA와 SQL을 혼용할 경우 영속성 컨텍스트의 오래된 값이나 갱신 유실을 방지하도록 경계를 명확히 한다. 트랜잭션 참여 및 flush·clear 정책은 상세 설계에서 확정한다.
- 다중 SKU 처리 순서, 잠금 대상, 낙관적 잠금 적용 범위, 충돌·교착 시 재시도는 시나리오에 따라 설계하고 테스트한다.
- DB 제약조건을 사용하여 중복 식별자와 유효하지 않은 수량 저장을 방어한다.
- 핵심 정합성 검증은 인메모리 대체 DB가 아닌 PostgreSQL에서 수행한다.

## 5. Outbox와 재처리

Outbox의 도입 근거는 다음 장애다.

> DB에 출고 지시를 저장한 뒤 WMS 호출 전에 프로세스가 종료되면, 저장된 업무와 외부 전달 결과가 달라질 수 있다.

출고 지시와 Outbox 메시지를 같은 트랜잭션으로 저장하고, 스케줄러가 메시지를 읽어 WMS로 전달한다.

- 전달은 중복될 수 있으므로 동일 출고 지시 ID와 수신 이벤트 ID에 대한 멱등성을 구현한다.
- 외부 HTTP 호출 중 DB 트랜잭션·행 잠금을 장시간 유지하지 않도록 작업 선점과 결과 반영을 분리한다.
- 작업 중 프로세스가 종료된 경우 다시 처리할 수 있도록 선점 만료와 복구 정책을 설계한다.
- 일시 오류, 결과 미확인, 업무 거절을 구분한다.
- 재시도 한도와 수동 확인 전환 기준은 상세 설계에서 확정한다.
- Outbox가 외부 시스템까지 정확히 한 번 실행을 보장한다고 주장하지 않는다.

## 6. 확장 시 검토할 기술

RAG, Kafka, Redis, Kubernetes는 규모 또는 요구사항 확장 시 검토할 후보다. 도입은 자동으로 결정하지 않으며, 측정 결과와 구체적인 필요를 근거로 판단한다. 특히 RAG는 처리량 확장보다 업무 지원 기능 확장에 해당한다.

| 후보 | 검토 계기 | 도입 전 확인할 사항 |
|---|---|---|
| RAG | 정책·운영 문서가 늘고, 현재 업무 상태와 연결한 근거 기반 설명이 필요해질 때 | 문서 갱신, 검색 품질 평가, 근거 인용, 권한 필터링, 현재 상태 조회 API와의 경계 |
| Kafka | 연동 대상·이벤트 소비자가 늘고, 독립적인 소비·재처리·이벤트 보관 요구가 커질 때 | 이벤트 키·순서, 중복 처리, 스키마 변경, 소비 지연, 운영 부담; DB Outbox와의 연결 방식 |
| Redis | 측정 결과 반복 조회의 DB 부하나 지연이 문제가 되고 캐시가 유효할 때, 또는 공유된 일시 상태가 필요할 때 | 캐시 무효화, 허용 가능한 오래된 값, 장애 시 동작; 재고·예약 정합성의 기준은 PostgreSQL에 유지 |
| Kubernetes | 다중 인스턴스·서비스 배포와 복구·확장 관리가 복잡해져 오케스트레이션이 필요할 때 | 단순한 배포 방식 대비 이점, 운영 비용, 상태 점검, 자원 제한, 설정·비밀 관리, 워커 중복 실행 안전성 |

RAG 도입 예시는 “이 요청은 왜 취소할 수 없나요?”에 대해 정책 문서를 검색하고, 권한이 확인된 업무 API로 현재 요청 상태를 조회하여 설명하는 기능이다. 검색 문서를 현재 재고·상태의 진실 공급원으로 사용하지 않는다.

## 7. 초기 완료 판단

초기 버전은 추가 인프라의 수가 아니라 다음 결과로 평가한다.

- 요구사항의 SC-01부터 SC-06까지 재현할 수 있다.
- 동시 처리와 재시도에도 재고 수량과 상태 규칙을 지킨다.
- 장애 발생부터 복구·수동 확인까지 이력으로 설명할 수 있다.
- 동일 환경에서 테스트와 데모를 다시 실행할 수 있다.
- 검증한 범위와 남은 한계를 문서로 명확히 구분한다.
