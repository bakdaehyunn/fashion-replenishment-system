# 패션 매장 재고 보충 및 출고 관리 시스템

요구사항 정의서 v0.1

이 문서는 공개된 패션·유통·창고 시스템 자료를 참고하여 정의한 포트폴리오 프로젝트의 운영 가정이다. F&F의 실제 내부 정책이나 시스템을 재현한 문서가 아니다.

## 1. 프로젝트 목적

매장에서 중앙 물류센터에 상품 보충을 요청하고, 승인·예약·피킹·출고·매장 입고까지 처리한다.

동시 요청, 피킹 부족, 입고 수량 차이, 외부 시스템 응답 유실 상황에서도 재고 수량과 업무 상태의 일관성을 유지하고, 미해결 업무를 추적한다.

- 같은 재고를 여러 요청에 초과 배정하지 않는다.
- 업무 상태 변경과 관련 재고 변경을 함께 처리한다.
- 외부 시스템의 응답 유실을 업무 실패로 단정하지 않는다.
- 요청 수량부터 최종 입고·차이 종결까지 추적할 수 있다.
- 중복 요청과 재처리로 재고가 두 번 반영되지 않는다.

## 2. 운영 환경과 범위

| 항목 | 운영 가정 |
|---|---|
| 브랜드 | 가상의 패션 브랜드 |
| 거점 | 중앙 물류센터 1곳, 매장 3곳 |
| 상품 | 스타일·색상·사이즈 조합별 SKU |
| 수량 단위 | 낱개 정수 |
| 보충 방식 | 매장 요청, 담당자 승인 |
| 재고 배정 | 승인 시 정상 출고 가능 재고 예약 |
| 부분 처리 | 요청 제출 시 부분 이행 허용 여부 지정 |
| 물류 연동 | 별도 WMS 시뮬레이터 |
| 입고 처리 | 출고 박스별 검수 |
| 기준 시간 | 저장은 UTC, 업무 화면은 한국 시간 |

첫 구현에서는 신청 즉시 제출한다. 임시 저장과 반려는 후속 기능으로 남긴다. 매장 직원은 활성 소속 매장에서 신청·조회·취소할 수 있다. 승인 담당자는 활성 소속 창고가 출발지인 요청만 조회·승인한다.

초기 범위는 매장 보충 요청부터 입고 차이 종결까지다. 구매·생산 입고, 매장 판매, 매장 간 이동, 고객 반품, 운송비 정산, 자동 수요 예측은 후속 범위로 둔다. 초기 재고는 출처가 명시된 기초 재고 등록으로 생성한다.

## 3. 사용자와 권한

| 역할 | 허용 업무 |
|---|---|
| 매장 직원 | 소속 매장의 보충 요청, 요청 조회, 취소 신청, 입고 검수 |
| 보충 승인 담당자 | 요청 승인·반려, 승인 수량 결정 |
| 물류 운영 담당자 | 피킹 부족 확인, 미출고 잔량 처리, 연동 결과 확인·재처리 |
| 재고 조정 담당자 | 실사 결과 확인, 재고 조정 승인, 수량 차이 종결 |
| WMS 연동 계정 | 출고 접수·피킹·출고 결과 전달 |

권한은 서버에서 검증한다. 매장 직원은 다른 매장의 요청이나 입고 내역을 변경할 수 없다.

## 4. 핵심 업무 개념

| 개념 | 정의 |
|---|---|
| 보충 요청 | 매장이 필요한 SKU와 수량을 제출한 문서 |
| 예약 | 특정 요청에 정상 재고를 배정한 기록 |
| 출고 지시 | WMS에 작업을 요청하는 업무 단위 |
| 피킹 | 출고할 실물을 창고 위치에서 확보하는 작업 |
| 출고 박스 | 실제 발송한 상품의 포장 단위 |
| 입고 검수 | 박스의 실제 도착 상품과 상태를 확인하는 작업 |
| 수량 차이 건 | 예정·보고 수량과 실제 확인 수량의 불일치 |
| 재고 이동 원장 | 재고 변경 원인과 수량을 기록하는 이력 |

보충 요청, 출고 지시, 입고 검수, 수량 차이는 각각 별도 상태를 가진다. 보충 요청의 전체 진행 상태는 하위 처리 결과를 기준으로 계산한다.

## 5. 재고 관리 원칙

| 구분 | 의미 |
|---|---|
| 정상 재고 | 정상 출고 또는 판매가 가능한 실물 |
| 보류 재고 | 파손·검수·차이 조사 등의 이유로 사용이 제한된 실물 또는 장부 수량 |
| 예약 재고 | 정상 재고 중 특정 요청에 배정된 수량 |
| 운송 중 수량 | 출고됐지만 도착·차이 처리가 끝나지 않은 수량 |

```text
가용 재고 = 정상 재고 − 유효 예약 재고
```

- 예약 재고는 정상 재고에 포함되는 수량이며 별도의 실물이 아니다.
- 피킹 완료만으로 창고 실물 재고를 차감하지 않는다.
- 출고 확정 시 창고 재고와 해당 예약을 차감하고 운송 중 수량을 생성한다.
- 정상 입고는 매장 정상 재고로, 파손 입고는 매장 보류 재고로 반영한다.
- 미확인 수량은 자동으로 창고나 매장의 정상 재고에 반영하지 않는다.
- 분실 확정 등으로 장부 수량을 줄이는 경우 승인된 조정 기록을 남긴다.

## 7. 주요 업무 규칙

### BR-01. SKU 간 자동 대체 금지

같은 스타일이라도 색상·사이즈가 다르면 별도 SKU로 처리한다. 재고가 부족하다고 다른 사이즈를 자동 배정하지 않는다.

### BR-02. 승인 정책

- 부분 이행 불허: 모든 요청 항목을 요청 수량대로 예약할 수 있어야 승인한다.
- 부분 이행 허용: 담당자가 승인 수량을 정할 수 있으며, 미승인 잔량을 구분해 남긴다.
- 승인 작업에서 결정한 모든 항목의 예약은 함께 성공하거나 함께 실패한다.
- 가용 재고 부족으로 승인에 실패한 경우 요청은 승인 대기 상태를 유지한다.

### BR-03. 미충족 잔량

부분 승인 또는 피킹 부족으로 남은 수량은 자동으로 처리 완료하지 않는다. 담당자는 잔량을 추가 이행 대기로 유지하거나, 사유를 기록하고 종결한다. 추가 출고는 새로운 출고 지시로 생성한다.

### BR-04. 피킹 부족

확보하지 못한 수량은 대체 위치 확인 후 처리한다. 재고 차이가 의심되면 예약 해제와 동시에 해당 수량을 조사 보류로 전환하여 재배정되지 않게 한다.

연관된 다른 예약까지 영향을 받는 경우 자동 조정하지 않고 담당자 확인 대상으로 남긴다.

### BR-05. 취소 경계

- 출고 지시 생성 전: 취소와 예약 해제를 함께 처리할 수 있다.
- 출고 지시 생성 후: WMS 작업 여부를 확인하여 취소한다.
- 응답 유실 중: 취소 요청을 기록하되 예약을 바로 해제하지 않는다.
- 출고 후: 일반 취소를 허용하지 않는다. 초기 버전에서는 반품 접수로 확장하지 않는다.

### BR-06. 타임아웃

통신 타임아웃은 업무 실패가 아닌 결과 미확인으로 처리한다. 동일 출고 지시 ID를 사용해 조회하거나 재전송한다.

### BR-07. 입고 차이

출고 수량과 정상 입고·파손 입고의 합계가 다르면 차이 건을 생성한다. 미확인 수량은 조사 후 추가 입고 또는 승인된 손실 처리로 해결한다.

### BR-08. 확정 기록 정정

확정된 출고·입고·재고 이동 기록을 덮어쓰거나 삭제하지 않는다. 정정은 원본과 연결된 보정 기록으로 남긴다.

## 8. 상태 설계 요구사항

정확한 enum과 전이 조건은 상세 설계에서 확정하되, 다음 상태를 구별해야 한다.

| 대상 | 구별해야 하는 상태 |
|---|---|
| 보충 요청 | 작성 중, 승인 대기, 반려, 이행 중, 완료, 취소 |
| 예약 | 유효, 출고로 소비, 취소·부족으로 해제 |
| 출고 지시 | 전달 대기, 접수 결과 미확인, 접수 완료, 작업 중, 출고 완료, 취소 확인 중, 취소 완료, 거절 |
| 입고 검수 | 검수 대기, 검수 중, 검수 확정 |
| 수량 차이 | 미해결, 조사 중, 해결 완료 |
| 연동 메시지 | 발송 대기, 처리 중, 재시도 대기, 전달 완료, 수동 확인 필요 |

다음 상태들은 서로 동일하게 취급하지 않는다.

- 메시지 전달 완료 ≠ 창고 작업 완료
- 피킹 완료 ≠ 출고 완료
- 입고 검수 확정 ≠ 수량 차이 해결
- 통신 오류 ≠ 출고 거절
- 업무 종결 ≠ 요청 수량 전량 충족

보충 요청 화면에는 전체 상태와 함께 요청·승인·출고·입고·미충족 종결 수량을 표시한다.

## 9. 핵심 시나리오 및 인수 기준

### SC-01. 정상 보충

요청·승인·출고·정상 입고가 모두 6장인 경우:

- 창고 정상 재고가 6장 감소한다.
- 매장 정상 재고가 6장 증가한다.
- 잔여 예약과 운송 중 수량은 0이다.
- 미해결 차이 건 없이 완료된다.

### SC-02. 동시 승인과 가용 재고 부족

초기 정상 재고 18장, 기존 예약 8장, 보류 재고 4장이다. A매장 7장, B매장 6장 요청을 동시에 승인한다.

- 신규 예약 합계는 10장을 초과하지 않는다.
- A가 먼저 7장을 확보했다면 부분 이행 불허인 B의 승인은 실패한다.
- B의 실패로 A나 기존 예약이 변경되지 않는다.
- 보류 재고 4장은 배정에 사용되지 않는다.

### SC-03. 피킹 부족

7장 예약 후 5장만 확보되고 대체 위치 확보도 실패한 경우:

- 피킹 결과와 부족 사유를 기록한다.
- 부분 이행 허용 시 5장 출고를 확정할 수 있다.
- 부족한 2장의 예약 해제와 조사 보류 처리를 일관되게 수행한다.
- 요청 잔량 2장은 추가 이행 대기 또는 사유 있는 종결로 남는다.
- 해당 2장을 즉시 다른 요청에 재배정하지 않는다.

### SC-04. 박스별 입고 차이

12장을 두 박스로 출고하고 정상 10장, 파손 1장, 미확인 1장으로 검수한다.

| 박스 | 출고 | 정상 입고 | 파손 입고 | 미확인 |
|---|---:|---:|---:|---:|
| C01 | 6 | 6 | 0 | 0 |
| C02 | 6 | 4 | 1 | 1 |
| 합계 | 12 | 10 | 1 | 1 |

- 매장 정상 재고는 10장 증가한다.
- 매장 보류 재고는 1장 증가한다.
- 미확인 1장은 운송 중 미해결 수량으로 추적한다.
- 창고 정상 재고를 자동 복원하지 않는다.
- 추가 입고 또는 손실 확정 전에는 차이 건이 종결되지 않는다.

### SC-05. 출고 응답 유실과 취소

WMS 접수 후 응답이 유실된 상황에서 취소 요청이 발생한다.

- 출고 지시는 결과 미확인 상태로 남는다.
- 예약을 즉시 해제하지 않는다.
- 동일 출고 지시 ID로 결과를 확인한다.
- WMS 취소 확정 시에만 예약을 해제한다.
- 이미 출고됐다면 취소를 거절하고 출고 사실을 반영한다.

### SC-06. 중복·충돌 이벤트

동일 출고 알림이 반복되거나 이벤트 순서가 바뀌는 경우:

- 같은 이벤트 ID의 동일 내용은 한 번만 반영한다.
- 같은 이벤트 ID에 다른 내용이 오면 충돌로 기록한다.
- 늦게 도착한 과거 이벤트로 업무 상태를 되돌리지 않는다.
- 선행 정보가 없어 처리할 수 없는 이벤트는 보류하고 재처리할 수 있다.

## 10. 시나리오 데이터 요구사항

데이터는 시나리오별로 재현 가능한 고정 식별자와 초기 조건을 가진다.

| 데이터 | 필요한 주요 정보 |
|---|---|
| SKU | 스타일, 색상, 사이즈, 바코드 |
| 재고 | 거점, SKU, 재고 상태, 수량 |
| 보충 요청 | 매장, 요청 항목, 희망일, 부분 이행 정책 |
| 예약 | 요청 항목, SKU, 예약·소비·해제 수량 |
| 출고 지시 | 외부 지시 ID, 요청 연결, 지시 수량 |
| 피킹 결과 | 작업 ID, 위치, 확보 수량, 부족 사유 |
| 출고 박스 | 박스 ID, 출고 지시, SKU별 수량 |
| 입고 검수 | 박스, 정상·파손 수량, 검수자 |
| 차이 건 | 유형, 수량, 근거, 담당자, 해결 결과 |
| 연동 기록 | 메시지 ID, 업무 ID, 발생·수신 시각, 재시도 횟수 |
| 감사 이력 | 수행자, 작업, 이전·이후 상태, 사유 |

각 시나리오에는 초기 데이터 → 실행 순서 → 예상 상태 → 예상 수량을 함께 정의한다. 데이터 양을 늘리는 성능 검증용 데이터셋은 별도로 구성한다.

## 11. 기술 및 비기능 요구사항

| 항목 | 요구사항 |
|---|---|
| 기술 기반 | Java 25, Spring Boot, PostgreSQL |
| 구조 | 업무 모듈을 분리한 단일 애플리케이션과 WMS 시뮬레이터 |
| 데이터 변경 | 업무 상태·재고·이력을 필요한 트랜잭션 경계에서 함께 반영 |
| 연동 신뢰성 | Transactional Outbox와 수신 이벤트 중복 방지 적용 |
| 동시성 | 단일 프로세스 메모리 잠금에 의존하지 않고 DB에서 정합성 보장 |
| 추적성 | 요청 ID와 출고 지시 ID로 로그·연동·재고 이력 연결 |
| 재시도 | 일시 오류와 업무 거절을 구분하고, 한도 초과 시 수동 확인 대상으로 전환 |
| 재현성 | Docker Compose로 동일 환경 실행 |
| DB 검증 | Testcontainers의 PostgreSQL로 트랜잭션·동시성 검증 |

응답 시간과 처리량 목표는 데이터 규모 및 측정 환경을 정한 뒤 수치로 확정한다. 검증 없이 대용량 처리나 고성능을 구현 성과로 표기하지 않는다.

## 12. AI 확장 범위

초기 구현에서는 RAG를 핵심 완료 조건에 포함하지 않는다.

후속 시나리오: 사용자가 “이 요청은 왜 취소할 수 없나요?”라고 질문하면, 취소 정책 문서를 검색하고 권한이 확인된 API로 현재 요청 상태를 조회하여 근거와 함께 설명한다.

정책 설명은 검색 문서에서, 현재 상태와 수량은 업무 API에서 얻는다. AI가 승인·취소·재고 조정을 직접 실행하는 기능은 후속 검토 대상으로 둔다.

## 13. 상세 설계에서 확정할 사항

- 엔티티·ERD와 수량 보존 규칙
- 상태 전이표, 부분 처리와 취소의 경계
- API, 멱등성 키의 적용 범위와 보관 정책
- 트랜잭션 경계, 잠금 순서, 충돌·교착 시 재시도 정책
- WMS 요청·응답·이벤트 계약과 순서 역전 처리
- 재고 차이로 기존 예약까지 영향을 받는 상황의 처리
- 과다 입고·예상 외 SKU의 보류 및 조정 절차
- 업무 완료·미충족 종결의 판정 조건
