# 파손 입고와 폐기 구현 명세

관련 문서 [OpenAPI](openapi.yaml) · [부족 검수](receiving-shortage-flow.md) · [운송 손실](receiving-transit-loss-flow.md)

도착 매장 직원은 최초 검수에서 SKU별 정상 수량과 파손 수량을 입력한다. 두 수량은 0 이상이고 합이 박스 출고량 이하여야 한다. 파손 수량을 생략하면 0이다. 정상 수량은 매장 정상 재고, 파손 수량은 매장 보류 재고로 반영한다. 둘을 합한 도착량이 출고량보다 적으면 차액만 부족으로 기록한다. 파손은 부족과 함께 발생할 수 있다.

파손 건은 최초 검수 상세별로 한 건 생성한다. 출발 창고에 활성 소속된 물류 운영 담당자가 조사 사유와 근거 번호를 기록해 폐기를 확정한다. 폐기 수량은 1 이상이며 현재 파손 보류 잔량 이하다. 일부 폐기 후 잔량이 남으면 OPEN을 유지하고, 전량 정산하면 RESOLVED로 바뀐다. 재검수를 통한 정상 재고 전환은 후속 범위다.

| 시점 | 정상 | 보류 | 운송 중 | 요청 |
|---|---:|---:|---:|---|
| 6장 출고 | 0 | 0 | 6 | 이행 중 |
| 정상 5·파손 1 검수 확정 | 5 | 1 | 0 | 이행 중 · 파손 조사 |
| 파손 1 폐기 | 5 | 0 | 0 | 완료 |

## API와 수량

최초 검수 경로에 선택 필드 `damagedQty`를 추가한다. 박스 상세는 최초 파손량과 파손 건 ID·잔량·상태를 반환하고, 출고 상세는 SKU별 파손 수량을 집계한다. `receivedQty`는 정상 입고 누계다. 운송 중은 출고량에서 정상 입고·파손 입고·운송 손실 누계를 빼서 계산하며, 폐기 후에도 파손 입고 사실은 유지한다.

폐기는 박스의 `/damages/{damageId}/disposals`에 POST한다. 기대 버전, 폐기 수량, 사유 및 근거 번호가 필요하다. 속하지 않는 파손 건은 404, 권한 부족은 403이다. 기존 성공 키를 먼저 확인하고 버전과 잔량을 검증한다. 최신 버전에서 잔량 초과나 종결 건은 409 RECEIPT_DAMAGE_CONFLICT다. 명령 종류는 DAMAGE_DISPOSAL이다. 해시에는 파손 건 ID·버전·수량·공백을 제거한 사유·근거를 포함한다. 기존 최초 검수의 파손 0 입력은 기존 정규화 해시와 호환한다.

## Flyway V6와 트랜잭션

- 최초 검수 상세에 0 이상인 파손 수량 컬럼을 추가한다. 기존 행은 0으로 둔다.
- 최초 검수 상세 FK가 유일한 파손 건을 추가한다. 최초 파손량과 남은 수량을 저장하고, 남은 수량이 0 이상이고 최초 수량 이하임을 제약한다.
- 폐기 전용 추가 기록에 파손 건 FK, 수량, 작업자, 시간, 사유·근거를 보존한다. 보류 원장은 최초 검수 입고의 양수 증감과 폐기의 음수 증감을 구분하며 각 처리 기록을 FK로 참조한다.
- 최초 검수는 검수와 부족·파손 건, 정상·보류 잔액, 관련 원장을 같은 트랜잭션에서 반영한다. 폐기는 요청 → 박스 → 파손 건 → 재고 키 순으로 접근하며, 잔량과 해당 매장·SKU 보류 재고를 조건부 차감한다. 파손 건에 배정된 수량만 처분할 수 있다.
- 두 명령 모두 요청 상태·버전·이력과 멱등성 결과를 함께 저장한다. 미확정 검수, 열린 잔량, 예약, 운송 중 수량, 미해결 부족 또는 파손이 모두 없어야 완료한다.

## 인수 기준

6장 중 정상 5·파손 1 확정 후 운송 중 0인데도 요청이 이행 중인지 확인한다. 담당자가 폐기하면 정상 5는 그대로이고 보류만 0이 되며 요청이 완료된다. 동일 키 재전송과 다른 키의 동시 폐기는 한 번만 차감된다. 타 거점·초과 수량은 반영하지 않는다. 폐기 원장 저장 실패를 주입해 보류 잔액·파손 잔량·요청 상태·성공 응답이 함께 롤백되는지 확인한다.
