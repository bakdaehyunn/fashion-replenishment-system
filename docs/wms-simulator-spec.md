# WMS 시뮬레이터 명세 v0.1

관련 문서: [요구사항](requirements.md) · [스택](technology-stack.md) · [테이블](table-design.md) · [보충 이행 상태](fulfillment-state-design.md)

## 1. 목적과 경계

창고의 출고 접수·피킹·포장·출고·취소를 최소한으로 재현하는 별도 프로그램이다. 지정된 초기 실물 데이터와 실제 수신한 출고 지시를 기준으로 결과를 계산하고, 지정 지점에서 통신 장애·중복·처리 순서를 재현한다.

보충 신청·승인·예약·부분 출고 결정·매장 입고 검수는 보충 관리 시스템에서 수행한다. 시뮬레이터가 보충 요청을 대신 생성하거나 업무 DB를 직접 변경하지 않는다. 실제 WMS의 위치 최적화·작업자 배정·설비 제어를 구현하지 않는다.

이 문서는 구현 전 명세다. 엔드포인트는 프로젝트 내부 계약 제안이며 외부 WMS의 실제 API가 아니다.

## 2. 사용자 흐름과 상황 설정 단위

```text
실행 환경과 초기 데이터 선택
 → 우리 시스템에서 보충 신청·승인
 → 출고 지시 생성 및 시뮬레이터 상황 설정
 → 우리 시스템에서 출고 전달 시작
 → 시뮬레이터 접수·작업·결과 전달
 → 우리 시스템에서 예외 처리·검수·최종 결과 확인
```

상황 적용 단위는 보충 요청이 아닌 출고 지시 ID다. 한 요청의 여러 출고 지시에 각각 다른 상황을 적용할 수 있다.

초기에는 출고 지시 생성 시 Outbox에 발송 보류 상태를 둘 수 있는 데모 프로필을 제공한다. 운영 기본 흐름은 자동 발송이며, 데모에서만 명시적으로 보류한다. 보류 지시는 DISPATCH_PENDING이고 화면에 발송 보류를 표시한다. 상황 설정 후 업무 시스템의 발송 시작 명령으로 Outbox를 발송 가능 상태로 바꾼다. 시뮬레이터가 우리 Outbox를 직접 변경하지 않는다.

상황 미설정 시 기본은 정상 처리다. 첫 전송 전에 설정된 접수 장애 프로필은 최초 접수 시 고정한다. 이후 이미 실행된 단계를 소급 변경하지 않는다.

## 3. 구성과 데이터 격리

- Java 25와 Spring Boot 기반 별도 실행 애플리케이션을 기본으로 한다.
- 업무 시스템과 독립된 저장소·DB 계정을 사용한다. 로컬에서는 같은 PostgreSQL 서버의 별도 데이터베이스로 구성할 수 있다.
- 데이터는 실행 ID(runId)로 격리한다. 업무 시스템의 시나리오 식별자와 출고 외부 ID에도 실행을 식별할 수 있도록 한다.
- 명령·초기 데이터·결정 결과·작업·전달 시도는 저장하여 재시작 후에도 확인한다.
- 시나리오 제어 API는 로컬 데모 전용으로 분리한다. 업무 연동 API와 인증 자격을 공유하지 않는다.
- 외부 실제 서비스나 실제 매장·작업자에게 메시지를 보내지 않는다.

## 4. 실행 모드

| 모드 | 용도 | 규칙 |
|---|---|---|
| FIXED | 개발·자동 테스트·면접 시연 | 지시별 명시적 시나리오와 파라미터 적용 |
| SEEDED_RANDOM | 여러 요청의 반복 검증 | 고정 시드와 버전이 있는 선택 알고리즘으로 시나리오 선택 |

작업 진행은 수동 STEP 또는 자동 AUTO다. FIXED/SEEDED_RANDOM은 상황 선택 방식이고 STEP/AUTO는 진행 방식이므로 별도 설정이다.

STEP은 작업 시작·피킹·포장·출고·이벤트 전달을 명시적 명령으로 진행한다. AUTO는 저장된 실행 계획에 따라 진행하지만, 부분 출고 승인 같은 업무 판단이 필요하면 중단하고 우리 시스템의 명령을 기다린다.

## 5. 초기 데이터와 창고 수량 계산

### 5.1 데이터 항목

| 데이터 | 필수 내용 |
|---|---|
| 상품 매핑 | 업무 SKU 코드, 창고 SKU 코드, 낱개 단위 |
| 창고 위치 | 위치 코드, SKU별 기초 실제 수량, 정상·보류 구분 |
| 장부 차이 근거 | 업무 시스템 기초 장부 수량과 실물 차이 사유 |
| 지시별 상황 | 프로필, 수량·지연·재전송 파라미터 |
| 박스 정책 | 최대 낱개 수량, 안정적인 SKU 정렬 규칙 |

위치 데이터는 시뮬레이터 내부의 최소 실물 모델이며 우리 시스템의 재고 예약과 구분한다.

### 5.2 계산 규칙

```text
위치별 확보 가능량 = 정상 실물량 - 다른 작업 및 현재 작업이 확보 중인 양
실제 피킹량 = min(지시 미확보량, 접근 가능한 위치들의 확보 가능량 합계)
최종 부족량 = 지시량 - 해당 작업의 최종 확보량
```

- 창고 확보는 작업에 실물을 점유시키는 행위다. 피킹과 출고 양쪽에서 정상 실물량을 중복 차감하지 않는다.
- 구현 모델은 정상 실물 총량을 출고 시 차감하고, 피킹 동안 확보량을 별도 기록하는 방식으로 고정한다.
- 여러 작업이 같은 SKU를 피킹하면 창고 저장소 트랜잭션에서 확보하여 실물 초과 배정을 방지한다.
- 위치 우선순위는 코드 오름차순으로 고정한다. 대체 위치까지 확인한 뒤 최종 부족을 보고한다.
- 정상 취소는 확보량을 해제한다. 출고는 정상 실물과 확보량을 함께 줄인다.
- 보류 실물은 확보에 사용하지 않는다. 수량은 음수가 될 수 없다.
- 출고·취소의 승자를 같은 작업 잠금 안에서 결정한다.

예: 업무 장부 정상 10, 창고 실제 정상 8, 차이 사유는 미발견 실물 부족. 우리 시스템이 9장을 예약·지시하면 시뮬레이터는 8장 확보·1장 부족을 보고한다. 결과 숫자를 임의로 반환하는 대신 초기 데이터에서 차이를 설명할 수 있어야 한다.

피킹 부족을 지정할 때 이미 실행 중인 다른 작업의 재고를 빼앗지 않는다. 부족량은 사전 fixture 또는 해당 작업에 제한된 접근 가능 재고 조건으로 설정한다. 공유 재고를 바꾸는 조정은 별도 명령과 이력으로 남긴다.

## 6. 시나리오 카탈로그

| ID | 프로필 | 발생 조건·동작 | 우리 시스템의 기대 처리 |
|---|---|---|---|
| WMS-01 | NORMAL | 충분한 실제 재고, 정상 이벤트 순서 | 접수→작업→출고, 검수 후 완료 |
| WMS-02 | PICK_SHORTAGE | 실제 접근 가능 수량이 지시량보다 적음 | 부족·보류·요청 잔량 반영, 부분 이행 판단 |
| WMS-03 | ACCEPT_THEN_TIMEOUT | 접수와 작업 저장 커밋 후 응답을 클라이언트 한도보다 지연 | 접수 미확인, 동일 지시 조회·재전송 |
| WMS-04 | DUPLICATE_CALLBACK | 실제 이벤트를 동일 ID·동일 본문으로 추가 전송 | 재고·상태 1회 반영 |
| WMS-05 | SHIP_BEFORE_CANCEL | 출고 확정을 먼저 커밋하고 취소 처리 | 출고 반영, 취소 거절 |
| WMS-06 | CANCEL_BEFORE_SHIP | 취소 확정을 먼저 커밋하고 출고 시도 | 출고 불가, 예약 해제 |
| WMS-07 | CALLBACK_UNAVAILABLE | 이벤트 저장 후 콜백 전달 일시 실패 | 결과 조회·재전송으로 복구 |
| WMS-08 | REORDER_CALLBACK | 실제 이벤트 생성 순서는 유지하고 전달 순서 변경 | 보류·조회·재처리, 상태 회귀 없음 |
| WMS-09 | REJECT_ORDER | 접수 시 명시적 업무 검증 실패, 작업 없음 | 거절 확정, 배정 해제, 예약 유지 |

WMS-03은 최초 신규 지시의 첫 응답에 한 번 적용하고 중복 재전송은 저장된 결과를 반환한다. 반복 장애는 별도 파라미터로 명시한다. WMS-07은 전달 실패만 유발하고 실제 창고 출고를 취소하지 않는다.

### 6.1 정상 예외와 잘못된 외부 이벤트의 구분

동일 이벤트 ID에 다른 본문, 취소 확정 후 모순된 출고 확정, 음수·과다 수량은 FAULTY_PROTOCOL 모드로 분리한다. 정상 랜덤 모드에서 생성하지 않는다. 해당 모드에서는 실제 창고 상태와 위조한 전달 데이터를 별도로 보관하여 충돌 처리만 검증한다.

## 7. 지시별 상황 설정

상황 설정에는 runId, externalOrderId, scenarioVersion, mode, scenarioProfile, parameters, progressMode를 포함한다.

파라미터 예:

- 피킹: SKU별 실물 fixture 참조 또는 접근 제한, 대체 위치 허용 여부.
- 응답 유실: 접수 후 지연 시간, 적용 횟수. HTTP timeout보다 큰 값으로 설정한다.
- 중복 전달: 원본 이벤트 ID, 추가 전송 횟수.
- 순서 역전: 전달할 이벤트 sequence의 명시적 순서.
- 경합: SHIP_FIRST/CANCEL_FIRST 처리 장벽.

프리셋은 하나의 업무 프로필과 호환 가능한 전달 장애를 조합한다. 예를 들어 피킹 부족+중복 알림은 가능하지만 접수 거절+정상 출고는 불가하다. 호환성 검증 실패 시 실행 전에 설정을 거절한다.

경합은 단순 sleep으로 우연한 승자를 기대하지 않는다. STEP 명령 또는 저장된 장벽 순서로 결과를 통제한다. 실제 다중 요청 경합 테스트에서는 승자보다 출고·취소의 상호 배타성과 수량을 검증한다.

## 8. 시드 기반 랜덤 실행

1. scenarioVersion과 fixtureVersion을 고정한다.
2. runSeed와 externalOrderId, 결정 항목 이름으로 안정적인 해시를 계산한다. 언어 기본 hashCode나 스레드별 공용 난수 호출 순서에 의존하지 않는다.
3. 저장된 가중치에 따라 호환 가능한 프로필과 파라미터를 선택한다.
4. 선택 결과를 실행 전에 저장한다. 동일 지시 재전송 시 다시 추첨하지 않는다.
5. 결과·선택 이유·적용 시점을 실행 로그에 남긴다.

초기 예시 가중치는 NORMAL 60, PICK_SHORTAGE 20, ACCEPT_THEN_TIMEOUT 10, REJECT_ORDER 10이다. 중복·순서 역전은 호환되는 지시에 별도 확률로 적용한다. 비율은 실제 현장 발생률을 주장하지 않는 테스트 설정이다.

재고 부족 프로필을 선택했으나 fixture 조건이 맞지 않으면 억지 수량을 생성하지 않는다. 실행 전 부적합으로 표시하거나 별도로 정의된 fixture를 선택한다. 자동 대체 시에도 최종 선택·사유를 기록한다.

동일 시드만으로 운영체제 스케줄링까지 동일해지지는 않는다. 완전 재현에는 초기 데이터, 버전, 입력 지시·명령 순서, 작업 배정 순서, 이벤트 전달 순서도 필요하다. 결정적 재생 모드에서는 저장한 순서를 그대로 사용한다. 자유 동시 실행은 불변식 검증 모드로 구분한다.

## 9. 업무 연동 API 초안

기본 경로는 `/wms/v1/runs/{runId}`다. runId는 데모 환경 구분이며 실제 WMS 계약에 필수라고 주장하지 않는다.

| 메서드·경로 | 기능 | 주요 규칙 |
|---|---|---|
| PUT /orders/{externalOrderId} | 출고 지시 접수 | 같은 ID·동일 본문은 기존 결과, 다른 본문은 409 |
| GET /orders/{externalOrderId} | 현재 상태·확정 사실 조회 | 상태, sequence, 피킹 revision, 박스, 취소 결과 반환 |
| POST /orders/{externalOrderId}/release | 부분 또는 전량 출고 실행 승인 | commandId로 멱등성, 최종 승인 항목·수량 검증 |
| POST /orders/{externalOrderId}/cancel | 취소 명령 | commandId로 멱등성, 출고와 원자적으로 판정 |
| GET /orders/{externalOrderId}/events | 원본 이벤트 조회 | sequence 이후 페이지 조회·누락 복구 |

PUT 입력은 requestReference, sourceWarehouseCode, destinationStoreCode, allowPartial, lines(lineId,skuCode,quantity)다. SKU별 중복·0 이하·미등록 매핑을 거절한다. 지시 본문은 정규화 후 해시를 비교한다.

접수 성공은 HTTP 200/201과 접수 상태를 반환한다. 5xx·타임아웃은 미접수를 보장하지 않는다. GET의 단순 404만으로 새 지시 생성·예약 해제를 허용하지 않는다. 취소가 접수보다 먼저 도착한 경우 cancellation tombstone을 기록하여 지연 도착한 같은 ID의 접수를 막는다.

release는 최종 피킹 결과와 정책에 맞는 수량만 허용한다. 부분 허용의 부족 회차는 우리 시스템 담당자가 결정한 수량과 잔량 해제 사실을 전달해야 하며 자동 출고하지 않는다. 정상 AUTO의 전량 확보 건은 WMS 내부 정책으로 포장·출고를 진행한다. 메시지 예제는 [정상 출고 구현 명세](outbound-normal-flow.md)를 따른다.

## 10. 이벤트 계약과 조회 복구

| 필드 | 의미 |
|---|---|
| eventId | 생성 후 불변, 전달 재시도에도 동일 |
| sourceSystem | WMS_SIMULATOR |
| runId / externalOrderId | 실행·업무 연결 |
| eventType / schemaVersion | 이벤트 종류·계약 버전 |
| sequence | 출고 지시별 1부터 증가하는 사실 순서 |
| occurredAt | 사실 확정 시각 |
| payload | 지시 항목 ID·SKU·수량·박스·피킹 revision·취소 결과 |

이벤트 종류는 ORDER_ACCEPTED, WORK_STARTED, PICKING_FINALIZED, PACKING_COMPLETED, SHIPMENT_CONFIRMED, CANCELLATION_CONFIRMED, CANCELLATION_REJECTED, ORDER_REJECTED다. 이벤트 본문과 eventId는 저장 후 수정하지 않는다. 피킹 정정은 새 이벤트·새 revision으로 보낸다.

피킹 결과는 해당 revision의 누적 최종 스냅샷이지 증분 수량이 아니다. 출고 확정은 회차 전체 박스·SKU·실제 출고량·미출고 종결량을 포함한다. 출고 지시별로 final shipment 한 번을 초기 계약으로 제한한다.

접수 전 취소 확정은 지시 ID별 tombstone과 CANCELLATION_CONFIRMED 이벤트(sequence=1)를 함께 저장한다. 해당 ID의 조회는 200과 CANCELLED를 반환하고 이벤트 조회는 원본 취소 이벤트를 반환한다. 늦은 PUT은 기존 취소 결과를 반환하며 작업을 생성하지 않는다. 접수와 취소는 같은 지시 키에서 직렬화한다.

업무 시스템은 runId·지시 ID별 마지막 연속 반영 sequence를 유지한다. Inbox의 이벤트 ID 중복과 별도로 동일 지시·순번의 다른 사건은 충돌로 보류한다. 다음 순번만 반영하며 커서는 업무 변경·Inbox 완료와 함께 커밋한다. 누락분은 마지막 반영 순번 이후 원본을 조회한다.

조회 응답은 마지막 sequence와 확정 사실을 제공한다. 누락 복구는 원본 events를 다시 수신하여 같은 Inbox 경로로 반영한다. 조회 결과를 근거 없이 새 eventId의 출고 이벤트로 재생성하지 않는다. 미래에 snapshot 반영이 필요하면 별도 멱등성 계약을 먼저 설계한다.

## 11. 콜백과 재전송

- 콜백 수신은 우리 시스템의 `/internal/wms/events`로 보낸다. 정확한 URL·인증은 설정값으로 관리한다.
- 우리 시스템은 Inbox에 내구성 있게 저장한 뒤 2xx 응답한다. 2xx는 업무 반영 완료를 뜻하지 않는다.
- 시뮬레이터는 타임아웃·일시 5xx에 재전송한다. 최초 이후 1초·5초·30초, 최대 3회 재시도를 데모 기본값으로 하고 설정 가능하게 한다.
- 인증·스키마 오류 등 영구 4xx는 자동 반복하지 않고 수동 확인 대상으로 기록한다. 중복 정상 이벤트는 2xx, ID·본문 충돌은 409로 구분한다.
- 재시도 소진에도 원본 이벤트는 보존하고 제어 API로 재전송한다.
- 출고 사실·이벤트·전달 대기 기록은 시뮬레이터 DB에서 함께 커밋한다. 프로세스 종료로 알림이 유실되지 않게 한다.

## 12. 제어 API와 화면

제어 경로 `/simulator/v1`은 업무 API와 분리한다.

| 기능 | 주요 입력·출력 |
|---|---|
| 실행 생성 | runId, seed, 모드, fixture·scenario 버전 |
| 상황 설정 | 출고 지시 ID, 프로필, 파라미터, STEP/AUTO |
| 작업 진행 | 작업 시작·피킹·포장·출고·취소 경합 단계 실행 |
| 전달 제어 | 특정 이벤트 전달·재전송·순서 지정 |
| 실행 조회 | 초기 수량, 현재 실물·확보량, 지시 상태, 이벤트·전달 결과 |
| 실행 중지·초기화 | 진행 중 워커 정지, 활성 호출 확인 후 테스트 데이터 초기화 |

화면은 실행 목록 → 출고 지시 목록 → 지시 상세로 구성한다. 지시 상세에는 업무 요청 참조, 선택 상황, 적용 여부, 창고 수량, 작업 상태, 이벤트 타임라인을 보여준다. 상황 설정·단계 실행·동일 이벤트 재전송 버튼을 제공한다. 보충 신청 버튼은 우리 업무 화면으로 연결하며 시뮬레이터 자체 신청 기능은 만들지 않는다.

초기화는 우리 업무 시스템 데이터를 몰래 삭제하지 않는다. 양쪽 fixture 재설정은 별도 테스트 하네스가 중지·초기화를 조율한다. 과거 run의 지연 콜백은 새 run에 반영되지 않아야 한다.

## 13. 시뮬레이터 저장 구조

업무 DB 테이블과 분리한 다음 최소 구조를 사용한다.

| 테이블 | 저장 내용 |
|---|---|
| sim_run | 시드·모드·버전·실행 상태 |

각 업무 키에는 runId를 포함한다. 박스·피킹 상세는 초기에는 검증된 이벤트 스냅샷으로 저장할 수 있으며 조회 요구가 커지면 정규 테이블로 분리한다. 실제 재고 판단과 작업 상태는 JSON 로그만으로 대체하지 않는다.

## 15. 구현 순서

1. FIXED + STEP, 정상 접수·조회·중복 방지 및 독립 창고 수량.
2. 피킹 부족·부분 출고 release·박스·이벤트 전달.
3. 접수 응답 유실·취소 경합·중복·순서 역전·재시작 복구.
4. SEEDED_RANDOM·자동 실행·저장된 계획 재생.

첫 목표는 정상·예외 한 건씩을 끝까지 재현하는 것이다. 랜덤 비율이나 반복 건수만으로 품질을 주장하지 않고, 실패 시 재현 정보와 수량 불변식 검증 결과를 함께 남긴다.

### 접수 응답 타임아웃 구현

`WMS_TIMEOUT_RUN_ID`가 전송된 run ID와 같으면 최초 PUT의 접수·첫 이벤트를 저장한 후 HTTP 응답을 8초 지연한다. 업무 서버의 HTTP 제한 시간은 5초다. 시연 중 미확인 상태를 관찰할 수 있도록 해당 작업과 저장된 콜백은 동일 지시 ID·동일 본문의 재전송까지 보류한다. 같은 ID의 다른 본문은 기존대로 409를 반환하고 보류도 유지한다.

업무 서버는 통신 오류나 일시적 서버 오류에서 아직 접수 이벤트가 반영되지 않은 전달 대기 지시만 ACCEPTANCE_UNKNOWN으로 바꾼다. 예약과 재고는 그대로 유지한다. Outbox의 저장된 본문과 기존 외부 지시 ID를 사용해 재전송하고 시도 횟수를 기록한다. 접수 콜백이 반영된 지시를 늦은 실패 결과가 미확인으로 되돌릴 수 없다. 저장된 WMS 이벤트는 기존 순번과 Inbox 경로로 처리한다.

### 출고와 취소 경합 구현

업무 API는 도착 매장 직원의 출고 취소를 202로 접수한다. 요청 잠금 아래 취소 상태를 REQUESTED로 바꾸고 취소 Outbox·요청 버전·기존 성공 응답을 함께 저장한다. 이 시점에는 예약을 유지한다.

취소 Outbox는 `POST /wms/v1/runs/{runId}/orders/{externalOrderId}/cancel`에 동일 `commandId`와 사유를 재전송한다. WMS는 지시 행을 잠가 출고 확정과 취소를 직렬화한다. 접수 전 취소는 CANCELLED 행과 첫 취소 이벤트를 저장해 뒤늦은 PUT이 작업을 만들지 못하게 한다. 접수 후 취소는 다음 순번에 CANCELLATION_CONFIRMED를 기록한다. 실제 출고가 먼저면 SHIPMENT_CONFIRMED 뒤에 CANCELLATION_REJECTED를 기록한다. 두 취소 이벤트는 원래 commandId를 payload에 포함한다.

업무 서버는 원본 순번으로 콜백을 반영한다. 취소 확정 시에만 배정과 예약을 해제하고 요청 잔량을 취소 종결한다. 실제 출고가 먼저 확정되면 출고 수량을 반영하고 취소는 거절로 표시한다. 취소를 재전송해도 WMS 판정과 결과 이벤트는 중복 생성되지 않는다.
