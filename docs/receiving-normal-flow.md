# 정상 입고 구현 명세

관련 문서 [업무 OpenAPI](openapi.yaml) · [보충 이행 상태](fulfillment-state-design.md) · [테이블 설계](table-design.md)

부족 검수까지 확장한 계약은 [부족 검수와 추가 입고](receiving-shortage-flow.md)를 따른다. 이 문서는 V3의 정상 입고 구현을 설명한다.

## 범위와 화면

도착 매장 직원이 출고 박스를 조회하고 상품별 실물 수량을 확인한 뒤 최초 정상 검수를 확정한다. 정상 수량이 박스의 출고 수량과 전부 일치하는 경우를 다룬다. 부족·파손·추가 입고·보정과 검수 임시 저장은 후속 단계에 추가한다.

출고 상태 화면에서 박스 목록과 출고·입고·운송 중 수량을 표시한다. 확정 버튼은 도착 매장의 매장 직원에게 활성화하고 서버에서도 역할과 현재 소속을 검사한다. 조회 권한은 출고 상세와 같다. 출고 확정 전 박스 목록은 비어 있으며 확정 대상은 저장된 출고 박스여야 한다. 검수 확정 후 응답의 버전과 상태를 화면에 반영한다.

## Flyway V3 설계

| 변경 대상 | 저장 및 제약 |
|---|---|
| replenishment_request | 상태 CHECK에 COMPLETED 추가 |
| receiving_inspection | ID, carton_id FK 및 UNIQUE, confirmed_by FK, confirmed_at. 정상 첫 검수만 저장하며 한 박스당 한 행 |
| receiving_inspection_item | inspection_id, carton_id, outbound_order_item_id, received_qty > 0. 검수당 출고 상세 중복 방지, 박스와 출고 상세의 복합 FK로 원본 박스 항목을 참조 |
| receiving_stock_movement | inspection_item_id UNIQUE FK, balance_id FK, normal_delta > 0, occurred_at. 매장 정상 재고 증감 원장 |
| command_result | 기존 키 구조에 RECEIPT 종류 사용. 입력 해시에 박스 ID와 정렬한 항목, 요청 버전을 포함 |

검수 상세의 carton_id는 검수 문서와도 복합 FK로 일치시킨다. 박스 최초 검수 UNIQUE는 현재 범위에 맞춘 제약이며 추가·보정 문서 도입 때 최초 검수 유형에 대한 제한으로 변경한다. 매장 재고 원장은 기존 창고 예약 원장의 필수 reservation_id를 유지하기 위해 별도 테이블에 둔다.

박스별 운송 중 수량은 출고 박스 항목 수량에서 유효 확정 입고량을 뺀 값으로 조회한다. 출고 상세 API의 inTransitQty도 박스별 계산의 합으로 변경한다. 상태와 수량을 조합하는 조회는 단일 질의 또는 일관된 읽기 스냅샷을 사용한다.

## 확정 트랜잭션과 완료 판정

1. 요청 행을 잠근다. 출고 지시와 박스가 요청에 속하는지 확인하고 도착 매장 권한을 검증한다.
2. 동일 명령 키의 성공 응답을 먼저 확인한다. 동일 본문은 당시 응답을 반환하고 다른 본문은 409 IDEMPOTENCY_CONFLICT다.
3. 최초 검수 존재 여부, 요청 버전, 요청 FULFILLING 및 출고 SHIPPED 여부를 차례로 검증한다. 이미 확정된 박스의 새 명령은 409 RECEIPT_ALREADY_CONFIRMED다. 버전 불일치는 409 VERSION_CONFLICT와 현재 버전을 반환한다.
4. 박스의 모든 출고 항목을 한 번씩 포함하고 입력 수량이 출고 수량과 같은지 확인한다. 누락·중복·다른 박스 항목·수량 불일치는 400으로 처리한다.
5. 검수와 상세를 저장하고 매장·SKU 키 순서로 재고 잔액을 생성 또는 갱신한다. 매장 정상 수량에 입고량을 더하고 매장 원장을 저장한다. 창고 재고와 요청 상세의 출고 누계는 유지한다.
6. 요청 버전을 한 번 올린다. 모든 출고 박스가 확정되고 열린 잔량·예약·운송 중 수량이 모두 0이면 COMPLETED로 전환한다. 여러 박스 중 일부만 확정되면 FULFILLING을 유지한다. 후속 차이·보정 기능을 추가할 때 기존 전체 완료 판정의 미해결 업무 조건을 함께 적용한다.
7. 검수·매장 재고·원장·요청 상태와 버전·이력·성공 응답을 같은 트랜잭션에서 커밋한다. 실패한 명령의 키는 소비하지 않는다.

## 인수 기준

| 사례 | 결과 |
|---|---|
| 6장 출고 후 정상 6장 확정 | 운송 중 0, 매장 정상 +6, 창고 재고 변화 없음, 요청 COMPLETED |
| 같은 키와 같은 입력으로 재전송 | 기존 201 및 검수 ID를 반환하고 매장 재고·원장 추가 없음 |
| 같은 박스에 새 키로 동시 확정 | 최초 한 건만 확정되고 다른 요청은 409 |
| 두 박스 중 첫 박스만 확정 | 나머지 박스 수량만 운송 중에 남고 요청은 FULFILLING |
| 수량 불일치 또는 다른 매장 계정 | 400 또는 403, 검수·재고 변경 없음 |
| 재고 갱신 후 원장 저장 실패 | 검수·재고·요청 버전·이력·성공 기록 모두 롤백 |
